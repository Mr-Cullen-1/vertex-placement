# Phase 1 — Core Backend Foundation

Status: complete. This document records what Phase 1 built on top of the
Phase 0 foundation ([ARCHITECTURE.md](./ARCHITECTURE.md),
[DATABASE.md](./DATABASE.md), [PRODUCT_RULES.md](./PRODUCT_RULES.md),
[ROUTES.md](./ROUTES.md), [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md) — all
still the source of truth for direction; this doc is the implementation
record on top of them). No visual UI was built — see "Scope boundary".

## Implemented services

All in `src/server/services/*.ts`. Every mutating (and most reading)
function takes an explicit `Actor` and starts with
`assertPermission(actor, "...")` (`src/server/rbac.ts`).

| Service | Responsibility |
| --- | --- |
| `placement-test.service.ts` | Test CRUD + DRAFT → PUBLISHED → ARCHIVED lifecycle |
| `question.service.ts` | Question + Option + QuestionMetadata authoring, publish |
| `placement-band.service.ts` | Scoring/placement band configuration |
| `candidate.service.ts` | Candidate create/read |
| `assignment.service.ts` | Assignment creation (candidate + test) |
| `invitation.service.ts` | Token generation/regeneration/revocation, token validation |
| `attempt.service.ts` | Start/resume, answer, submit, the shared finalization pipeline, admin result detail |

Domain logic these wrap (pure, no Prisma — `src/domain/*`):
`scoring/engine.ts` (raw score, difficulty progression, topic
performance, band matching), `tokens/token.ts` (generation, hashing,
state-machine validation), `attempts/option-order.ts` (Fisher-Yates
shuffle) and `attempts/timing.ts` (expiry math), `results/present.ts`
(student summary vs. admin detail views).

Two thin `"use server"` wrappers exist (`src/server/actions/*.ts`) —
`attempt-actions.ts` for the token-gated student flow,
`admin-actions.ts` for a handful of admin operations — proving the
services are callable as real Server Actions. **No page imports them
yet**; that's Phase 2.

## Database migration

Two migrations, both applied and committed under `prisma/migrations/`:

1. `20260903110702_init` — the full Phase 0 schema, generated by
   `prisma migrate dev`.
2. `20260903111521_active_invitation_unique_index` — hand-written raw
   SQL adding a **partial unique index**
   (`ON placement_invitations ("assignmentId") WHERE status = 'ACTIVE'`),
   since Prisma's schema DSL can't express partial unique indexes. See
   "Security review" below for why.

One schema change from the Phase 0 design, made for security reasons
(not a redesign of the architecture — see "Decisions" below):
`PlacementInvitation.token` → `PlacementInvitation.tokenHash`. The
plaintext token is never persisted, only its SHA-256 hash.

Verified: `prisma validate`, `prisma generate`, and an actual
`prisma migrate dev` run against a real local PostgreSQL 18 instance all
succeed (see "How to run locally").

## Authentication

Unchanged in shape from Phase 0 (Auth.js v5, Credentials provider, JWT
sessions, no public registration) — Phase 1 didn't need to touch
`src/lib/auth.ts` or `src/proxy.ts`. What Phase 1 added:

- `src/lib/actor.ts` — `getActorOrThrow()`, the one place outside
  `src/lib/auth.ts` allowed to call `auth()`. It resolves the session
  into a plain `{ userId, role }` `Actor` and throws `UnauthorizedError`
  if there isn't one. This is what a Server Action calls before handing
  control to a service — services themselves never touch Next.js/session
  APIs, keeping them testable without a request context.
- The Super Admin bootstrap (`prisma/seed.ts`) is idempotent (verified —
  see "Verification results"), hashes with bcrypt (cost 12), and never
  logs the password. Run via `SEED_SUPER_ADMIN_EMAIL` /
  `SEED_SUPER_ADMIN_PASSWORD` env vars — see "Seed / bootstrap commands".

## RBAC implementation

`src/server/rbac.ts` is the single permission matrix — a
`Record<UserRole, Permission[]>` plus `assertPermission(actor, permission)`.
Permissions: `test:read`, `test:write`, `question:write`, `band:write`,
`assignment:write`, `invitation:write`, `candidate:read`, `result:read`,
`analytics:read:standard` / `analytics:read:full`, `export:standard` /
`export:full`, `import:write`. `SUPER_ADMIN`'s permission set is
`ADMIN`'s plus authoring/full-access permissions — there is no separate
enumeration to drift out of sync.

This is deliberately centralized instead of ad hoc `if (role === ...)`
checks scattered across services, per the instruction that future routes
"cannot accidentally bypass" authorization. Verified with both direct
unit tests of the matrix (`tests/unit/rbac.test.ts`) and integration
tests exercising real services with real Actors
(`tests/integration/authorization.test.ts` — Admin genuinely cannot
create/edit a test, add a question, or modify a band; Admin genuinely can
create assignments and invitations; Super Admin can do both).

## Token lifecycle

Implemented in `src/domain/tokens/token.ts` (pure) +
`src/server/services/invitation.service.ts` (persistence). Summary — full
detail in [ARCHITECTURE.md](./ARCHITECTURE.md#token-lifecycle):

- `generateInvitationToken()` — 256 bits from `crypto.randomBytes`,
  base64url-encoded. Not derived from any ID.
- Only the SHA-256 hash is stored (`tokenHash`); the plaintext exists in
  memory at generation time and in the returned `IssuedInvitation`, never
  logged, never persisted.
- `generateInvitation` refuses to create a second `ACTIVE` invitation for
  an assignment (`InvitationAlreadyActiveError`) — both at the
  application level and, as a race-proof backstop, at the database level
  (the partial unique index).
- `regenerateInvitation` revokes the current `ACTIVE` invitation and
  creates a new one against the same assignment in one transaction;
  never touches `PlacementTest` or `PlacementAssignment`.
- `validateTokenAndLoad` is the single choke point every token-bearing
  request goes through — hashes the incoming token, looks it up, and
  throws the specific `DomainError` for `NOT_FOUND` / `REVOKED` /
  `ALREADY_USED` / (reserved) `EXPIRED`.

## Attempt lifecycle

Implemented in `src/server/services/attempt.service.ts`. Full detail in
[ARCHITECTURE.md](./ARCHITECTURE.md#attempt-lifecycle). The load-bearing
design decision made during this phase's security review:

**Every public function takes the invitation token, not an `attemptId`.**
`getAttemptQuestions`, `submitAnswer`, and `submitAttempt` all re-resolve
`token → invitation → attempt` on every call
(`requireAttemptIdForToken`), re-running the full `ACTIVE`/`USED`/
`REVOKED` check each time. A student has no session, so the token is the
only thing the server can treat as a credential; an `attemptId` is an
internal database key that must never be trusted as caller-supplied
input (explicitly required — see "Security review" below).

- `startOrResumeAttempt(token)` creates on first visit, resumes on
  refresh, and — critically — **never creates a second attempt**: the
  `invitationId` unique constraint on `PlacementAttempt` is the final
  backstop against a create/create race (caught via Prisma's `P2002` and
  turned into a resume instead of an error).
- Resuming an attempt whose test was archived after the attempt started
  still works — only *starting a new* attempt is blocked by the
  `PUBLISHED` check (see "PlacementTest lifecycle" in ARCHITECTURE.md;
  this asymmetry was a bug caught during this phase's own review, fixed
  and covered by a regression test).
- Option display order is randomized once (`buildOptionOrder`, crypto
  Fisher-Yates) and stored on the attempt; every subsequent read replays
  the same order from storage.

## Submission / finalization pipeline

One private function, `finalizeAttempt(attemptId, trigger)`, is the only
place a `PlacementResult` is ever created — called identically by manual
submission (`submitAttempt`) and by lazy auto-submission (discovered
inside `getAttemptQuestions`/`submitAnswer`/`startOrResumeAttempt` via
`autoFinalizeIfExpired` whenever `now >= expiresAt`). Steps, all inside
one transaction:

1. Atomic guard: `UPDATE ... WHERE id = ? AND status = 'IN_PROGRESS'`.
   If zero rows update, another request already finalized this attempt —
   throw `DuplicateSubmissionError`. This is what makes concurrent
   double-submission safe (see "Security review").
2. Compute scoring (`domain/scoring/engine.ts`) from the test's
   `PUBLISHED` questions, the attempt's answers (missing = unanswered =
   incorrect, never a crash), and the test's `PlacementBand` rows.
3. Create the `PlacementResult` row (raw score, percentage, completion
   time, difficulty progression, topic performance, placement band).
4. Mark the invitation `USED`, the assignment `COMPLETED`.
5. Determine canonical: query for an existing completed, canonical
   attempt under the same assignment; if one exists, this attempt is
   `isCanonical = false`, otherwise `true`. **Never assumes "latest =
   canonical."**

There is no scheduled sweep/cron job — per the approved Phase 0
decision, enforcement is on-access only.

## Scoring architecture

`src/domain/scoring/engine.ts`, pure, no Prisma. Takes
`(questions, answers, bands)` and returns raw score, difficulty
progression (grouped by `QuestionMetadata.difficultyBand`, first-
occurrence order), topic performance (same, by `topic`), and a
placement-band match (`percentage` falling within a band's
`[minPercentage, maxPercentage]`, or `null` if none configured/matches).
No CEFR cutoffs, no Macmillan-specific claims, and no band values are
hard-coded anywhere — `PlacementBand` rows are business configuration a
Super Admin creates per test. The illustrative difficulty ranges from the
Phase 1 brief (Beginner 1–6, Elementary 7–20, etc.) are realized only as
`QuestionMetadata.difficultyBand` string labels on individual questions
— never as a magic-number range check anywhere in code.

## Canonical result logic

Covered above (finalization pipeline, step 5) and tested explicitly:
`tests/integration/attempt-lifecycle.test.ts` creates a second attempt
under an already-completed assignment (simulating a future retake at the
data level, since no retake UI exists) and asserts the second one's
`isCanonical` is `false` while the first's stays `true` — proving the
logic checks "does a canonical completed attempt already exist," not
"is this the most recent attempt."

## Automated tests

`npm test` (Vitest 4). 56 tests across 7 files, all passing.

- **Unit** (`tests/unit/`, no database): `rbac.test.ts`, `token.test.ts`,
  `option-order.test.ts`, `scoring.test.ts` — pure domain logic,
  deterministic (a seeded PRNG stands in for the crypto RNG in
  `option-order.test.ts` so shuffle assertions are reproducible without
  weakening the production randomness).
- **Integration** (`tests/integration/`, real database):
  `attempt-lifecycle.test.ts`, `invitation-lifecycle.test.ts`,
  `authorization.test.ts` — exercise the real service layer against a
  real, ephemeral PostgreSQL instance. Covers: attempt creation/resume
  (including "never a duplicate attempt"), full scoring correctness
  (all-correct / all-incorrect / partial / unanswered), server-side
  expiry enforcement on every entry point, a genuine concurrent-request
  race for duplicate submission (`Promise.allSettled` on two simultaneous
  `submitAttempt` calls — exactly one succeeds), archiving mid-attempt,
  canonical result determination, invitation generate/regenerate/revoke,
  the partial-unique-index constraint itself (bypassing the service layer
  on purpose to prove the database backstop works, not just the
  application check), and the full Admin-cannot/Super-Admin-can
  authorization matrix.

Why a real database instead of mocks: several of the above (the
create/create race, the double-submit race, the partial unique index,
transaction behavior in the finalize pipeline) are not meaningfully
testable against a mocked Prisma client — they're testing what the
database itself guarantees under concurrency. See "How to run locally"
for how that database is provisioned without Docker or a system install.

## How to run locally

1. `npm install`
2. Local PostgreSQL, no Docker/system install required:
   `npm run db:local:start` (leave running in its own terminal — real
   PostgreSQL 18 via the `embedded-postgres` binary distribution,
   data persisted under `.pgdata/dev/`, gitignored). Prints the
   `DATABASE_URL` to use (already set in `.env` by default:
   `postgresql://postgres:postgres@127.0.0.1:55432/vertex_placement`).
3. `npm run db:migrate` — applies both committed migrations.
4. `npm run db:seed` — see "Seed / bootstrap commands" below.
5. `npm run dev`, sign in at `/admin/login`.
6. `npm test` — boots its own separate, fully ephemeral PostgreSQL
   instance on port 55433 (`tests/setup/global-setup.ts`), applies the
   migrations, runs all 56 tests, and tears the database down
   afterward. Safe to run alongside `npm run dev`/the dev database — they
   never share a port or a data directory.

A known Windows-specific quirk with the embedded PostgreSQL binary: its
shutdown can occasionally leave one orphaned worker process holding the
test port after a run. `global-setup.ts` detects and auto-recovers from
this at the start of the next run (kills the leftover process by
matching its command line against the test data directory, scoped
narrowly so nothing else on the machine is touched); if that recovery
itself fails, it fails fast with a clear error rather than hanging.

## Security review

Checked against the brief's explicit list:

| Area | Finding / mitigation |
| --- | --- |
| Password hashing | bcrypt, cost 12 (`seed.ts`, `auth.ts`). Never logged. |
| Token entropy | 256-bit `crypto.randomBytes`, base64url. Verified never to repeat across 50 generations in tests. |
| Token storage | **Fixed during this phase.** Originally schema'd (Phase 0) as a plaintext-stored unique `token` column. Changed to `tokenHash` (SHA-256) before any data existed — see "Database migration". |
| Token exposure | Grepped the entire `src/` tree for `console.*` calls touching token values — none exist. `invitation.service.ts` carries an explicit comment warning against adding one. |
| Authorization | Centralized in `rbac.ts`, called at the top of every service mutation; verified by both unit and integration tests. |
| Server-side validation | Zod schemas on every service's external input (`candidate.service.ts`, `placement-test.service.ts`, `question.service.ts`, `placement-band.service.ts`, `assignment.service.ts`, `attempt.service.ts`'s `submitAnswerSchema`). |
| Attempt ownership | **Fixed during this phase.** `getAttemptQuestions`/`submitAnswer`/`submitAttempt` originally took a bare `attemptId` — since students have no session, that made the ID itself a de facto bearer credential, but `cuid()`s aren't designed as unguessable secrets the way the invitation token is. Changed all three to take the plaintext token and re-derive the attempt internally on every call. |
| Candidate data exposure | Student-facing functions never return candidate PII. `getAdminResultDetail` requires `result:read` against a real authenticated Actor. |
| Score manipulation | Scoring is always computed server-side from `Option.isCorrect` + persisted answers; no score/percentage is ever accepted as input. |
| Timer manipulation | `expiresAt` is computed once server-side at attempt creation from `startedAt + PlacementTest.durationSeconds`; never accepted from the client. |
| Duplicate submission | Atomic `updateMany(... WHERE status = 'IN_PROGRESS')` guard inside the finalize transaction. Verified with a genuine concurrent-request test (`Promise.allSettled` on two simultaneous submits — exactly one succeeds, exactly one `PlacementResult` row exists). |
| Replay of completed tokens | `validateTokenAndLoad` rejects `USED` invitations; since every attempt-touching function re-resolves through it, a spent token can't be replayed against any of them. |
| Race on invitation creation | Partial unique DB index (`assignmentId` WHERE `status = 'ACTIVE'`) backstops the application-level check — verified by a test that bypasses the service layer to hit the constraint directly. |

No unnecessary security abstractions were added beyond these — e.g. no
token-storage layer beyond a plain hash-and-compare, no bespoke crypto.

## Decisions made during Phase 1 (flagged, not silently changed)

These are the only points where implementation diverged from a literal
reading of the Phase 0 documents — each was a genuine issue found during
build-out or the security review, not a preference change:

1. **`PlacementInvitation.token` → `tokenHash`.** Security fix (plaintext
   bearer-token-equivalent storage). See "Database migration" and
   "Security review" above.
2. **Attempt-touching functions take a token, not an `attemptId`.**
   Security fix (untrusted client-supplied ID as a de facto credential).
   See "Attempt lifecycle" and "Security review" above.
3. **`startOrResumeAttempt` only enforces `PUBLISHED` when starting a
   *new* attempt, not when resuming one.** Bug fix — the original
   version would have interrupted an in-progress attempt the moment its
   test was archived, contradicting the documented archive behavior. See
   "PlacementTest lifecycle" in ARCHITECTURE.md.
4. **A partial unique index, added via a hand-written migration**, since
   the schema DSL can't express one. Not a redesign — it enforces a rule
   that was already the intended business rule ("at most one ACTIVE
   invitation per assignment"), just previously only checked in
   application code.

None of these required re-deciding anything already settled by you in
the Phase 0 review (invitation expiry, auto-submit mechanism, canonical
result, git history) — those stand exactly as approved.

## Phase 1.5 — Supabase connection

Status: complete. Connects the project to a dedicated Supabase
PostgreSQL database. No schema change, no domain/service code change, no
UI. Two small, additive infrastructure changes:

- **`prisma.config.ts`** now reads `DIRECT_DATABASE_URL` instead of
  `DATABASE_URL` for the CLI datasource (`migrate`/`db seed`/`studio`).
  `src/lib/db.ts` (the runtime driver adapter) is unchanged — it still
  reads `DATABASE_URL`. This is the pooled-vs-direct split described
  when this phase was proposed: the app should never hold long-lived
  direct connections, and migrations need a connection DDL/shadow-DB
  operations can rely on.
- **`.env.example`** documents both variables and which Supabase
  connection string (from the dashboard) each maps to.

**A real constraint discovered while connecting, not an architecture
issue:** Supabase's true "Direct connection" host
(`db.<project-ref>.supabase.co:5432`) resolves to an IPv6 address only,
with no IPv4 address, unless the project has Supabase's paid IPv4
add-on. This network doesn't have outbound IPv6 connectivity, so that
host was unreachable (`P1001`). Supabase's own documented workaround —
used here — is the **Session Pooler** connection string for
`DIRECT_DATABASE_URL` instead: same Supavisor pooler host as the
transaction pooler, port 5432 instead of 6543. Session mode gives each
client a dedicated backend connection for the session's duration (unlike
transaction mode, where the backend can change between transactions), so
it behaves like a direct connection for `prisma migrate`'s purposes
while still being IPv4-reachable. `DATABASE_URL` (the app's runtime
connection) correctly stays on the true transaction pooler, port 6543.

Verified, against the real Supabase database:

- `prisma migrate deploy` — both committed migrations applied cleanly
  (via the session-pooler `DIRECT_DATABASE_URL`); `prisma migrate status`
  reports the schema up to date afterward.
- The hand-written partial unique index
  (`placement_invitations_one_active_per_assignment`) is present and
  correctly defined — checked directly via `pg_indexes`, not assumed.
- The **runtime** path — `@prisma/adapter-pg` over `DATABASE_URL` (the
  transaction pooler) — works end to end: five sequential parameterized
  queries and a Prisma model-API query all succeeded with no
  prepared-statement errors, confirming the adapter's default of not
  caching named prepared statements (verified earlier from its type
  definitions) really is compatible with Supabase's transaction-mode
  pooling in practice, not just in theory.
- `npm run dev` against Supabase: `/`, `/admin` (redirects, unauthenticated),
  and `/admin/login` all respond as expected.
- A local-only bug this change would otherwise have introduced: the test
  suite's `global-setup.ts` invokes `prisma migrate deploy` against its
  own ephemeral local database by overriding env vars for that
  subprocess — it was only overriding `DATABASE_URL`, which the CLI no
  longer reads. Fixed by also overriding `DIRECT_DATABASE_URL` for that
  subprocess. Caught before it could silently break `npm test`;
  confirmed fixed — full suite re-run, 56/56 passing.
- Full verification suite re-run after these changes: `tsc`, `eslint`,
  `next build`, and `npm test` all clean.

No real data was seeded into Supabase (no Super Admin, no sample test) —
only the schema. `.env` itself was edited directly by the user with
their Supabase credentials and was not read or echoed by the assistant
into any output, doc, or commit.
